# פרומפט: מעבר לתשתית תורים חיצונית ומנגנון בסגנון Step Functions

> פרומפט מסודר להעברת מנוע ה-Workflow הקיים ממודל "Worker קורא ומחכה לתשובה"
> למודל אסינכרוני אמיתי מונחה-אירועים, מעל תור חיצוני (SQS / שירות דומה),
> בסגנון AWS Step Functions. נכתב על בסיס הקוד הקיים כדי לשמר את מה שעובד.

---

## 1. מטרה (בקצרה)

תהליך הפנייה חייב להתקדם דרך **אירועים ותורים**, לא דרך קריאה סינכרונית אחת.
פעולה מול מערכת חיצונית יכולה לקחת **זמן לא ידוע** (שניות עד ימים). לכן אסור
שתהליך/Worker יחזיק משאב בזמן ההמתנה. כל "המתנה" צריכה להיות **מצב עמיד
בבסיס הנתונים/בתור**, שמתעורר רק כשמגיע אירוע תוצאה (callback) או בבדיקה
תקופתית (polling).

---

## 2. מה כבר קיים ואסור לשבור (המצב ההתחלתי)

המנוע הנוכחי כבר אסינכרוני-חלקית. יש לשמר את הרכיבים הבאים:

- **מכונת מצבים מוגדרת ב-JSON** — `DefinitionJson` בטבלת `Processes`:
  States / Transitions / Fields / Documents. העורך וה-API נשארים.
- **מצב המתנה + מעברי תוצאה אוטומטיים** — מעבר עם `BusinessAction` מכניס את
  הפנייה למצב המתנה, ומוגדרים לו שני מעברים: `businessSuccess` ו-`businessFailure`
  (ולידציה ב-`Engine.ValidateDefinition`). זה כבר הבסיס האירועי — להרחיב, לא לזרוק.
- **ה-Adapter (חוזה אחיד)** — `BusinessHandler` עם `Run` ו-`Recover`,
  מקבל `BusinessRequest(OperationId, ProviderId, Inputs)` ומחזיר
  `BusinessResult(Success, Message, Data)`. המנוע אדיש ל"איך" (HTTP/SQL/…).
- **Recover + Receipts (exactly-once)** — `OperationId` = מזהה ה-Outbox;
  ה-Target שומר Receipt, וכך קריאה חוזרת לא מבצעת פעמיים. **הלב של האמינות —
  לשמר במלואו.**
- **הגנות עמידות שכבר נבדקו** — claim/lease/heartbeat, fenced ack,
  WaitingState (409), backoff + חסימה אחרי 5 כישלונות עסקיים.
- **מנוע התהליך (`Engine.Execute`) לא משנה את הסמנטיקה שלו** — רק *מי קורא לו
  ומתי* משתנה (אירוע תוצאה במקום סיום סינכרוני של ה-Worker).

**מה כן משתנה:** היום ב-`BusinessActions.Deliver` ה-Worker קורא ל-`handler.Run`
ו**מחכה** עד שה-Target עונה (כולל `Task.Delay` ב-slow). זה הדבר היחיד שצריך
להיעקר: הקריאה מול ה-Target לא תחזיק את ה-slot לאורך ההמתנה.

---

## 3. העיקרון המנחה (סגנון Step Functions)

כל צעד בתהליך הוא אחד משניים:
1. **Task סינכרוני-מהיר** — פעולה שמסתיימת מיד (עדכון DB, שליחת מייל). נשאר כמו היום.
2. **Task אסינכרוני (ממתין)** — "שלח בקשה, שחרר את המשאב, המתן לאות שהצליח".
   זה ה-pattern שחסר. בשפת Step Functions: `waitForTaskToken` / Activity.

העיקרון: **לעולם לא להחזיק thread/slot בזמן המתנה חיצונית.** המצב "ממתין"
נשמר בבסיס הנתונים, והתעוררות מגיעה מאירוע חיצוני.

---

## 4. הדרישות הפונקציונליות

### 4.1 שליחת בקשה (dispatch)
- כשתהליך מגיע לצעד אסינכרוני: לשלוח הודעת בקשה **לתור חיצוני** (לא לקרוא ולחכות).
- ההודעה נושאת `OperationId` (= מזהה ה-Outbox הקיים), `ProviderId`, `Inputs`,
  ו**TaskToken/CallbackToken** ייחודי לצעד הזה.
- מיד לאחר השליחה: הפנייה נשארת ב**מצב המתנה**, וה-slot/המשאב משתחרר. אין המתנה.

### 4.2 קבלת תוצאה — שני מסלולים
- **callback (מועדף):** ה-Target קורא חזרה ל-endpoint שלנו עם ה-TaskToken
  והתוצאה. ה-endpoint מאמת את ה-token, מוודא שהפנייה עדיין ממתינה (WaitingState),
  ומריץ את מעבר התוצאה (`businessSuccess`/`businessFailure`) דרך `Engine.Execute`.
- **polling (גיבוי):** job תקופתי שעובר על פעולות ממתינות שחרגו מסף זמן ושואל
  את ה-Target "סיימת?" לפי `OperationId` — זה בדיוק מה ש-`Recover` כבר עושה.

### 4.3 טיפול בזמן לא ידוע
- לכל צעד ממתין: **timeout לוגי** מוגדר (לדקות / שעות / ימים). פקיעת timeout
  אינה כישלון אוטומטי — לפני כל מסקנה חובה לשאול את ה-Target לפי `OperationId`
  (ייתכן שהפעולה בוצעה והאות אבד).
- heartbeat/visibility של התור צריך להתאים לפעולות ארוכות, או שהצעד יישמר
  כ"ממתין" בבסיס הנתונים ולא יישען על visibility של הודעה בתור.

### 4.4 exactly-once ואמינות
- `OperationId` + Receipt אצל ה-Target הם המקור היחיד לאמת. אסור ש-callback
  כפול, polling כפול, או retry יבצעו פעולה פעמיים.
- callback מאוחר מבעלים/טוקן שאינו תקף עוד — נדחה, לא משנה את הפנייה (כמו
  ה-fenced ack וה-WaitingState היום).

### 4.5 תאימות לאחור
- תהליכים שאינם משתמשים בצעד אסינכרוני ממשיכים לעבוד בלי שינוי.
- כל ה-`/checks` הקיימים חייבים לעבור ללא נסיגה (תהליכים והרשאות).

---

## 5. דרישות לא-פונקציונליות

- **אין תלות קשיחה בספק ענן אחד.** להפריד את "תור/שירות אירועים" מאחורי
  ממשק (interface) כך שאפשר להחליף SQS / Azure Queue / RabbitMQ / Step Functions
  ללא נגיעה במנוע. הקוד שמכיר את הספק יושב בשכבת Infrastructure בלבד.
- **שחזור מלא אחרי קריסה.** צעד ממתין חייב לשרוד restart של השרת ושל ה-Worker.
- **ניטור:** אפשר לראות לכל פנייה באיזה צעד היא ממתינה, מתי נשלחה הבקשה,
  וכמה זמן היא ממתינה.
- **פשטות מול כוח:** אם רוב הצעדים מהירים, אסור שהתשתית החדשה תסבך אותם —
  צעד מהיר נשאר מהיר.

## 6. שאלות הכרעה (לפני כתיבת קוד)

1. **איזו תשתית תור?** SQS מנוהל / Azure / RabbitMQ עצמי / Step Functions ממש?
   (לכל אחת מחיר תפעולי ותלות שונים.)
2. **callback או polling כברירת מחדל?** האם מערכות ה-Target שלכם *יכולות*
   לקרוא חזרה, או שרובן רק עונות כששואלים?
3. **כמה ארוכות ההמתנות באמת?** שניות? דקות? ימים? זה קובע אם צריך
   Step Functions ממש או שהרחבת ה-Outbox מספיקה.
4. **כמה instances/Workers ירוצו במקביל?** זה מצדיק (או לא) את claim/lease
   שכבר קיים.
5. **מי מפתח את צד ה-Target?** (עלתה בפגישה — לרוב גורם אחר; ה-callback
   דורש שיתוף פעולה שלו.)

## 7. קריטריוני קבלה (איך יודעים שהצלחנו)

| בדיקה | התוצאה הנדרשת |
|---|---|
| צעד אסינכרוני נשלח | הבקשה יוצאת לתור; הפנייה במצב המתנה; שום thread/slot לא תפוס |
| Target עונה דרך callback | מעבר התוצאה רץ; הפנייה מתקדמת; token נצרך פעם אחת |
| Target איטי (שעות/ימים) | הפנייה ממתינה ללא החזקת משאב; מתעוררת רק באירוע |
| callback כפול / token לא תקף | נדחה; הפנייה לא משתנה פעמיים |
| פעולה בוצעה אך האות אבד | polling/Recover מחזיר את ה-Receipt ללא ביצוע כפול |
| timeout לוגי פקע | נשאלת תוצאה לפי OperationId לפני כל retry; לא נקבע כישלון שרירותי |
| קריסת שרת/Worker באמצע המתנה | הצעד הממתין שורד restart ומתעורר כרגיל |
| תהליכים ישנים ללא צעד אסינכרוני | עובדים ללא שינוי; כל ה-/checks עוברים |

---

## 8. גבולות מפורשים (מה לא בטווח)

- לא לשנות את סמנטיקת מכונת המצבים (States/Transitions/Guards/Effects).
- לא לשנות את חוזה ה-Adapter (`BusinessRequest`/`BusinessResult`/`Run`/`Recover`).
- לא לבנות fan-out / ריבוי מנויים לאירוע אחד בשלב זה.
- לא להחליף את בסיס הנתונים של הפניות; רק להוסיף תשתית תור/אירועים לצידו.

---

## 9. פלט נדרש מהמממש

1. תכנון קצר: היכן נשברת ההמתנה הסינכרונית, ואיזה interface מפריד את ספק התור.
2. מימוש הצעד האסינכרוני (dispatch -> token -> callback endpoint -> polling גיבוי).
3. בדיקות קבלה מול Target מקומי מבוקר (האטה + כשל יזום), כמו שכבר קיים
   ב-`LocalAddressTarget` (`slow` / `reject` / `interruptOnce`).
4. דוח קצר: מה מומש, מה נבדק בפועל, מה נשאר כ-limitation.
